3. AUTHENTICATION
============================================

REGISTER:
POST /api/auth/register/

Example:
{
  "username": "customer1",
  "email": "customer@example.com",
  "first_name": "Ali",
  "last_name": "Khan",
  "password": "UseAValidPassword123!",
  "password_confirm": "UseAValidPassword123!"
}

Public registration creates a CUSTOMER account.

LOGIN:
POST /api/auth/login/

Example:
{
  "username": "customer1",
  "password": "UseAValidPassword123!"
}

Email can also be used instead of username.

LOGIN RESPONSE:
- message
- token
- user

USER ROLES:
ADMIN
WORKSHOP_OWNER
CUSTOMER
MECHANIC

PROFILE:
GET /api/auth/profile/

LOGOUT:
POST /api/auth/logout/

AUTHENTICATION HEADER:
Authorization: Token YOUR_TOKEN

CONTENT TYPE:
application/json

4. WORKSHOP OWNER APPLICATION
============================================

Customer application:
POST /api/workshops/applications/

View own applications:
GET /api/workshops/applications/

Admin application list:
GET /api/workshops/admin/applications/

Optional filters:
?status=PENDING
?status=APPROVED
?status=REJECTED

Admin review:
PATCH /api/workshops/admin/applications/ID/review/

APPROVAL BODY:
{
  "status": "APPROVED"
}

REJECTION BODY:
{
  "status": "REJECTED",
  "admin_note": "Reason for rejection"
}

Admin approval changes the account role to WORKSHOP_OWNER.

Check backend/workshops/serializers.py for exact application
request fields before building the application form.

7. WEBSITE TO MOBILE QR PAIRING
============================================

REQUIRED FLOW:

1. Workshop Owner logs into the website.
2. Website displays a Connect Mobile App option.
3. Website requests a pairing code.
4. Website displays the code as a QR image.
5. Flutter app opens its QR scanner.
6. Mobile app scans the website QR.
7. Flutter sends the scanned code to the backend.
8. Backend verifies the code.
9. Backend returns an authentication token.
10. Mobile app stores the token securely.

A. WEBSITE GENERATES QR DATA

POST /api/auth/website-pairing/generate/

Requires authenticated WORKSHOP_OWNER.

Header:
Authorization: Token WEBSITE_OWNER_TOKEN

No request body required.

Example response:
{
  "message": "QR pairing code generated.",
  "code": "ONE_TIME_SECRET_CODE",
  "expires_at": "TIMESTAMP",
  "expires_in_seconds": 300
}

The website must convert the returned code into a QR image.
The backend returns QR data, not an image.

B. FLUTTER SCANS QR

Use a Flutter QR scanner package.
Extract the exact code from the QR.

C. FLUTTER EXCHANGES THE CODE

POST /api/auth/website-pairing/exchange/

Request:
{
  "code": "SCANNED_ONE_TIME_SECRET_CODE"
}

No Authorization header is required for this endpoint.

Successful response contains:
- message
- token
- user

QR SECURITY:
- Expires after 5 minutes.
- Can only be used once.
- Backend stores a SHA-256 hash of the code.
- Only an active WORKSHOP_OWNER can successfully pair.
- Invalid, expired and reused codes are rejected.
- Never put a password or existing login token inside the QR.

IMPORTANT TOKEN NOTE:
The current implementation reuses the user's existing DRF token.
Website and mobile share the same token.
Logging out deletes that token for both clients.

WEBSITE QR DISPLAY AND FLUTTER QR SCANNING:
These frontend features still need to be implemented by Mustafa
and Shaheer.
