# 1. PROJECT ARCHITECTURE

Smart Auto Care consists of three connected components:

1. **Flutter Mobile Application** — Customer and Workshop Owner mobile experience.
2. **Website** — Workshop Owner desktop experience.
3. **Backend** — Django REST Framework API and shared database.

All applications must use the same backend and database.

The backend is the source of truth for authentication, permissions, workshop information, customer information, and business operations.

### User roles

- ADMIN
- WORKSHOP_OWNER
- CUSTOMER
- MECHANIC

Public registration creates a CUSTOMER account. A customer must submit a Workshop Owner application, and an administrator must approve it before the account becomes a WORKSHOP_OWNER.

**Important:** Use the term Workshop Owner consistently, not Workshop Manager.


### Connection addresses

| Environment            | Backend address                    |
| ---------------------- | ---------------------------------- |
| Same computer          | `http://127.0.0.1:8000`            |
| Android emulator       | `http://10.0.2.2:8000`             |
| Physical Android phone | `http://YOUR_COMPUTER_LAN_IP:8000` |

For physical-device testing:

1. Connect the phone and computer to the same Wi-Fi.
2. Start Django using:

```cmd
backend\.venv\Scripts\python.exe backend\manage.py runserver 0.0.0.0:8000
```

3. Configure Django `ALLOWED_HOSTS`.
4. Allow port 8000 through Windows Firewall.
5. Configure Flutter to use the computer's LAN IP.

**Important:** Flutter currently has this base URL in `mobile_app/lib/services/api_config.dart`:

```dart
static const String baseUrl = 'http://127.0.0.1:8000/api/';
```

This works for local computer testing and can be used with USB debugging and `adb reverse tcp:8000 tcp:8000`.

It must be changed for Android emulator or physical-phone testing.

Never use `127.0.0.1` on a physical phone to reach the computer's backend.

# 8. WEBSITE ↔ FLUTTER QR LOGIN

## Intended QR login design — IMPORTANT

The agreed project design is:

**A logged-out website displays a QR code. An authenticated Workshop Owner scans it using Flutter and explicitly approves or rejects the website login. The website receives the login token only after approval.**

Scanning alone must never authenticate the website.

### Intended workflow

1. Workshop Owner opens the website.
2. Website displays the Connect Mobile App / QR login option.
3. Website requests a new pairing code without requiring an existing website login.
4. Backend creates a random one-time code and stores its SHA-256 hash.
5. Website converts the returned code into a QR image.
6. Workshop Owner logs into the Flutter application.
7. Workshop Owner opens the Website QR Login screen.
8. Flutter scans the website QR.
9. Flutter sends the scanned code to the backend using the authenticated Workshop Owner token.
10. Backend verifies the pairing request.
11. Flutter displays the website login request.
12. Workshop Owner explicitly selects Approve or Reject.
13. Backend records the decision.
14. Website checks the pairing exchange endpoint.
15. If approved, the backend returns the Workshop Owner's authentication token and user information.
16. Website establishes the authenticated session.

### Backend QR endpoints

Generate:

```http
POST /api/auth/website-pairing/generate/
```

Scan:

```http
POST /api/auth/website-pairing/scan/
```

Approve or reject:

```http
POST /api/auth/website-pairing/approve/
```

Exchange / website polling:

```http
POST /api/auth/website-pairing/exchange/
```

### Scan request

```json
{
  "code": "SCANNED_QR_CODE"
}
```

### Approval request

```json
{
  "code": "SCANNED_QR_CODE",
  "approved": true
}
```

Use `false` to reject.

### Exchange request

```json
{
  "code": "QR_CODE_FROM_WEBSITE"
}
```

The exchange endpoint can return:

- HTTP 202 while approval is pending.
- HTTP 200 after successful approval, containing `message`, `token`, and `user`.
- An error for invalid, expired, rejected, or already-used codes.

### QR security requirements

- Random one-time code.
- Five-minute expiry.
- SHA-256 hash stored in the database.
- Code can only be used once.
- Only an active WORKSHOP_OWNER can approve.
- Website must not authenticate before approval.
- Invalid, expired, rejected, and reused codes must be rejected.
- Never place a password or existing authentication token inside the QR code.

### IMPORTANT: Current backend issue

The current backend implementation still has a mismatch with the agreed design:

- `WebsitePairingGenerateView` currently requires `IsWorkshopOwner`.
- It creates the pairing record with `user=request.user`.
- The intended design requires a logged-out website to generate the pairing code.
- The Flutter scanner already requires an authenticated Workshop Owner and explicitly asks for approval.

Therefore, the backend generation logic must be adjusted to support the intended logged-out website flow. The generated pairing should initially be unclaimed, and the authenticated Flutter Workshop Owner should claim it during scanning.

The scan, approval, and exchange operations must continue to verify the code, ownership, approval status, expiry, and one-time-use rules.

**Do not tell the website developer that the logged-out QR workflow is fully ready until this backend mismatch is fixed and tested.**

### Token behavior

The current backend uses Django REST Framework token authentication.

The exchange endpoint reuses the user's existing token through `Token.objects.get_or_create()`.

This means the website and mobile application can share the same DRF token. Logging out deletes that token, which invalidates it for both clients.

The website must store the returned token securely and send it in authenticated API requests.
